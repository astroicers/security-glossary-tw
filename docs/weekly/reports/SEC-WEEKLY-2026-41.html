  • 🔴 立即緩解Fortinet FortiMail CVE-2026-104286（CVSS 9.8，零時差，尚無修補版本）並啟動應急鑑識：（1）所有FortiMail部署立即執行兩項緩解措施之一——停用IBE（Identity-Based Encryption）功能支援，或完全停止管理介面的網頁存取並透過ACL/防火牆規則嚴格限制來源IP僅允許信任地址；（2）依Fortinet發布的入侵指標（IoC），掃描FortiMail系統的可疑檔案、設定異動及非預期連線至外部IP；（3）稽核所有FortiMail管理員帳號，確認無非預期帳號（FortiBleed同期活動已確認攻擊者會建立後門帳號）；（4）7.2分支使用者需同時升級至7.4以上版本，以在修補版本（7.4.9、7.6.7、8.0.2）發布時能立即套用；（5）持續監控Fortinet官方公告，有修補版本時立即部署。
  • 🔴 立即修補Cisco Catalyst SD-WAN Manager CVE-2026-76504（CVSS 9.8，CISA KEV 9/30）並稽核入侵跡象：（1）確認所有Cisco Catalyst SD-WAN Manager部署版本，立即升級至修補版本（20.9.10.1、20.12.8.2、20.15.6.1、20.18.4.1、26.1.2.1或26.2.1）——Cisco明確指出無任何暫時緩解措施；（2）修補前或無法立即修補時，評估限制SD-WAN Manager管理介面的網際網路可達性；（3）稽核SD-WAN Manager稽核記錄（audit log）中，自9月起針對 /j_security_check 及 /%6a_security_check 路徑的異常請求；（4）確認所有SD-WAN Manager的管理員帳號列表，搜尋非預期帳號或組態異動；（5）若確認受損，應立即隔離受影響Manager並評估受管邊緣設備的完整性。
  • 🔴 立即修補所有Atlassian Data Center產品CVE-2026-21589並針對Jira+Crowd整合部署啟動應急回應：（1）確認所有Bitbucket、Confluence、Jira Software、Jira Service Management、Bamboo、Crowd、Crucible及Fisheye Data Center自管部署版本，立即升級至最新修補版本；（2）Jira整合Crowd的部署優先處理：立即主動輪換crowd.properties中的應用程式憑證（即便尚未確認遭利用亦應輪換，因主動利用已確認），並透過Crowd管理介面稽核所有管理員帳號，刪除非預期帳號；（3）修補前的暫時緩解：透過WAF規則封鎖含「..::」序列的HTTP請求，並限制管理介面的外部網路存取；（4）稽核過去7天的存取記錄，搜尋對WEB-INF路徑的任何GET請求（攻擊特徵）；（5）雲端版本已自動修補，無需額外操作。
  • 🔴 稽核所有Fortinet設備管理員帳號並強制輪換憑證（對應FortiBleed大規模攻擊）：（1）立即盤點所有FortiGate及FortiMail設備，登入管理介面核查管理員帳號列表，刪除任何非預期帳號；（2）若無法登入自身設備（疑似帳號遭竄改），立即透過實體主控台重設管理員密碼；（3）強制輪換所有Fortinet設備的管理員密碼（包含服務帳號）並啟用多因素驗證；（4）確認Fortinet設備是否啟用管理員登入稽核，並設定異常登入告警（非工作時間、來自未知IP的登入）；（5）確認FortiGate SSL-VPN設定未遭異動（攻擊者常藉此建立持久後門通道）。
  • 🔴 台灣學術機構及關鍵基礎設施確認FishHub/MicroScan感染指標並配合CISA AA26-281A補丁截止：（1）依CISA通報AA26-281A核查所有新增至KEV的Flax Typhoon相關CVE，確認已在10月11日前完成修補或已套用緩解措施；（2）台灣大學及研究機構應立即核查主機及網路端點是否存在FishHub或MicroScan的已知IoC（聯繫TWCERT/CC或CISA取得最新IoC清單）；（3）稽核IT環境中是否有非預期的遠端管理工具、不明的外部SSH連線或異常的資料存取記錄；（4）確認電子郵件閘道的防釣魚設定，針對近期聲稱的學術活動或政策議題的可疑郵件加強警戒（對應Talos UAT-11985的AitM釣魚活動）；（5）若懷疑遭滲透，立即向TWCERT/CC（twcert.org.tw）報告並啟動鑑識調查。
  • 🟡 稽核GitHub Actions工作流程並強制輪換受GhostAction影響的CI/CD憑證：（1）核查所有公開及私有Repository中是否存在2026年8月31日後新增的 security-audit.yml 或 github_actions_security.yml 工作流程，若存在應視為已遭入侵；（2）受影響Repository立即強制輪換所有已暴露的GitHub Secrets、AWS/GCP/Azure Token、Kubernetes憑證及AI供應商API金鑰（OpenAI、Anthropic等），五個月後仍有效的竊取憑證顯示被動等待失效並不可靠；（3）稽核GitHub Organization的第三方App授權及已安裝的GitHub Actions，確認無非預期的高權限操作；（4）未來的安全強化措施：將工作流程依賴項固定至特定commit SHA（而非版本標籤），並啟用Step Security Harden-Runner等工具監控Actions執行環境中的可疑網路連線。
  • 🟡 確認備份策略應對雲端勒索軟體（對應IDCF Cloud事件）：（1）核查在APAC地區使用雲端服務（IDC Frontier、AWS、Azure、GCP或其他IaaS）的工作負載，確認是否有異地（跨雲或本地）的獨立備份，且備份資料與主要環境的帳號憑證完全隔離（防止攻擊者以相同憑證刪除備份）；（2）測試備份還原程序的實際可用性——IDCF Cloud事件揭示許多客戶依賴雲端服務商的備份而非維護獨立備份，造成資料難以復原；（3）參考3-2-1備份原則：三份備份、兩種媒體、一份離線或異地存放，確保單一供應商遭攻擊不會導致業務資料完全滅失；（4）評估關鍵系統（ERP、資料庫、郵件）的業務連續性計畫（BCP），確認雲端供應商服務中斷時的備援方案。
